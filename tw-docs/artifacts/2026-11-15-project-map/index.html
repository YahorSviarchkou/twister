Twister: карта проекта

Система управления велосипедной мастерской. Изначально монолит JavaFX под Windows, сейчас переезжает на модули с прицелом на плагины и веб-версию.

состояние на 15.11.2026 ветка exp последний коммит 28.03.2026 последние правки в рабочей копии 12.04.2026 Java 21 · Spring Boot 3.2.5 · JavaFX

Коротко. Самая зрелая часть проекта — tw-workflow: стейт-машины трёх уровней заказа, сервисы и 138 тестов. Модель в tw-core и JPA-слой в tw-persistence-api в основном готовы. Между ними нет связующего слоя: из 11 DAO-портов не реализован ни один, а единственный CustomerDaoImpl возвращает null.

Новое desktop-приложение пока не стартует, плагинной системы нет, CI собирает только старый монолит на JDK 17. Работа стоит с апреля, и около 64 файлов (стартер, мапперы, desktop) существуют только в незакоммиченной рабочей копии.

04 · СТАТУСЫ И КАСКАДЫ

Стейт-машины tw-workflow

Переходы взяты из TransitionTable. Оранжевые номера отмечают состояния, после которых WorkflowOrchestrator запускает каскад; расшифровка ниже. Красный пунктир: переходы, которых требует задуманный процесс, но в таблице их нет.

Каскады WorkflowOrchestrator.execute

1Заказ ACCEPTED → создаётся RepairTask в статусе CREATEDработает 2Заказ REJECTED → задаче отправляется CANCELИз OPEN всегда падает: задачи ещё нет, NoSuchElementException откатывает транзакцию. Юнит-тест мокает задачу и скрывает баг.баг 3Задача CANCELED → CANCEL каждому пунктуПункты в READY или CANCELED не имеют перехода CANCEL, бросается IllegalStateException, откатывается всё. Заказ при прямой отмене задачи остаётся ACCEPTED.баг 4Все пункты READY → задаче FINISH_TASKЗапрос findAllTaskItemsStatusesByTaskId возвращает всю историю, а у каждого пункта есть запись CREATED, поэтому allMatch(READY) не выполнится. CANCELED-пункты тоже не исключаются.баг 5Задача READY → заказу GENERATE_INVOICEСтатус уходит в WAITING_PAYMENT, но RepairInvoiceService.generateRepairInvoice никто не вызывает. В коде: // todo gen invoice needed? or manual.наполовину

06 · DAO-ПОРТЫ

Порты workflow против слоя persistence

Чтобы контекст desktop-приложения поднялся, каждый порт нужен как бин. Репозитории почти совпадают с портами, но нет ни мапперов целиком, ни адаптеров.

Порт (tw-workflow)РепозиторийМапперАдаптерЗамечание
CustomerDaoестьпустойзаглушкаCustomerDaoImpl в desktop, все методы возвращают null
ReferenceDao<T> ×6естьестьнетCountry, ServiceType, SpareBrand, SpareType, TransportBrand, TransportType
SpareDaoбез findByNameестьнетв CompositeReferenceRepository нет findByName
TransportDaoбез findByNameестьнетто же
RepairOrderDaoестьциклынетOrder → Task/Invoice → Order: риск StackOverflow в MapStruct
RepairTaskDaoестьпустойнет
RepairTaskItemDaoестьпустойнет
RepairInvoiceDaoестьциклынетмапперы Invoice и Order используют друг друга
StatusHistoryDao<Order>естьбаг idнетworkflowItem → workflowItemId не маппится, NOT NULL упадёт
StatusHistoryDao<Task>естьпустойнет
RepairTaskItemStatusHistoryDaoсемантикапустойнетJPQL отдаёт всю историю, а нужен последний статус каждого пункта
UserDaoесть——порт пустой, UserService пустой
Архитектурное решение, которое нужно принять первым. Где живут адаптеры. Сейчас persistence не зависит от workflow, а адаптер положен в desktop, значит веб-приложению пришлось бы писать их заново. Вариант: вынести порты в отдельный модуль (или в tw-core) без Spring Data типов, а адаптеры держать в tw-persistence-api. Тогда desktop и web подключают одну и ту же реализацию. Попутно убрать Page/Pageable из сигнатур портов и зависимость workflow от starter-data-jpa.
