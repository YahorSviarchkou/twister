Twister MVP: полный десктоп без плагинов, пять модулей и одно правило зависимостей

Эталон для первой рабочей версии (веха M3). Домен и сценарии не знают ни про JavaFX, ни про базу. UI ходит только в use cases, хранилище подключается в runtime. Свой JavaFX-стартер оставляем, но чиним и дописываем: бутстрап, фабрику контроллеров, потоки, навигацию.

Статус: дизайн, Proposed. Опирается на ADR 0004–0006 и roadmap от 21.11.2026. Расходится с ADR 0004 в одном месте, оно отмечено в разделе «Модули».

Спицы — это порты. Слева ведущие адаптеры (экраны вызывают use cases), справа ведомые (use cases вызывают хранилище, печать, часы). Зависимости идут только к ступице.

Скоуп MVP: всё, что нужно мастерской, чтобы отказаться от бумаги

Фаза 1 из продуктового переосмысления: принять, отремонтировать, выдать. Один ПК, одна база, несколько пользователей по очереди. Скоуп M3 на доске пока открытый вопрос, поэтому список предварительный.

Входит

  • Клиенты и их транспорт (велосипеды, самокаты, электросамокаты), поиск по телефону, номеру рамы или серийному номеру
  • Приём: жалоба, чек-лист, фото из файлов, квитанция и бирка с QR
  • Диагностика, смета, согласование (кто, как, порог «без звонка»)
  • Пункты работ: услуга и запчасти с количеством, мастер
  • Доска заказов по статусам, карточка заказа
  • Счёт, оплата частями (наличные, карта вручную), выдача
  • Склад: остатки, приход, списание по заказу
  • Справочники: услуги и прайс, запчасти, бренды, типы
  • Пользователи, роли, PIN, журнал «кто что сделал»
  • Автобэкап, восстановление, установщик для Windows

Следующие фазы

  • Планшет механика по Wi-Fi, LAN-сервер (фаза 2)
  • Уведомления клиенту: Telegram, SMS (фаза 2)
  • Статус по QR и согласование по ссылке (фаза 2)
  • Поставщики, заказ запчастей, точки дозаказа (фаза 3)
  • Фискальная касса там, где её требует закон; сдельная оплата мастеров (фаза 3)
  • Отчёты по марже и загрузке (фаза 3)
  • Сезонные напоминания, гарантия (фаза 4)

Не делаем вообще в MVP

  • Плагины, SPI, UI-слоты, дескрипторы плагинов
  • tw-app-web, tw-fx-plugin-*: исключить из сборки
  • Синхронизация двух баз, облако, мультиарендность
  • Обобщённый Asset, другие вертикали
  • Генерация таблиц из аннотаций на доменных классах
  • Перенос данных legacy, пока нет реальной мастерской с данными

Модули: пять в сборке, UI не видит JPA даже на этапе компиляции

Названия модулей пока не меняем: переименование в tw-api / tw-kernel / tw-store-jpa из ADR 0004 стоит делать, когда появятся вторая сборка или плагины. Сейчас это только шум в истории.

Правило зависимостей

Стрелки только к домену. Домен не импортирует ничего, кроме JDK. Use cases не знают про JPA и JavaFX. Экраны вызывают use cases и запросы, но не репозитории. Хранилище подключено к приложению как runtimeOnly: класс JPA в контроллере просто не скомпилируется.

Gradle закрывает границы между модулями, ArchUnit закрывает границы внутри модуля: домен без фреймворков и граница пакета vehicle (ADR 0005).

Что выпадает из ADR 0004 на время MVP

tw-api как отдельный модуль портов не нужен: порты лежат в tw-workflow, а tw-workflow зависит только от spring-context и spring-tx. Когда появится LAN-сервер (фаза 2), отделить порты будет механической работой, если правило зависимостей соблюдалось.

tw-shell-javafx отдельно от сборки появится вместе с app-desktop-client. До этого экраны живут в tw-app-desktop.

База данных: почему SQLite, а не H2 или PostgreSQL

Решение пока предварительное: в roadmap это отдельная задача и ADR. Рекомендация — SQLite, переносимый SQL и тесты на файле. Тогда переезд на PostgreSQL в фазе 5 стоит недели работы, а не переписывания.

JavaFX-стартер: оставляем свой, чиним девять мест и дописываем бутстрап

Готовой поддерживаемой интеграции JavaFX и Spring Boot 4 нет. FxWeaver — последний релиз 19.09.2024, автор называет его побочным проектом, совместимость с Boot 4 не подтверждена. mvvmFX не обновлялся с 2018 года. Документированный путь (Josh Long, статья BellSoft 2025 года) — это и есть то, что делает наш стартер: Spring в init(), сцена в start(), фабрика контроллеров из контекста.

Стартер не знает ничего о Twister. Его переиспользуют tw-app-desktop сейчас, клиент LAN-сервера в фазе 2 и любой другой ваш JavaFX-проект. Веб-оболочка его не использует.

Код по слоям: эталон, на который ориентируются агенты

Примеры на одном сценарии: заказ, смета, согласование. Это ожидаемая форма кода, а не готовая реализация: имена и сигнатуры можно менять, правила зависимостей нельзя.

Существующий движок из tw-workflow переезжает в домен и получает guards. Агрегат сам решает, можно ли переход, и UI спрашивает у него же, какие кнопки активны.

Вся схема статусов заказа из ADR 0005 в одном месте, рядом с guard-ами. Таблицу можно сверять с диаграммой state-order.mmd глазами.

Агрегат без сеттеров. Изменение статуса всегда идёт через машину, пишет историю и копит событие. Транспорт (велосипед, самокат) известен заказу только как SubjectId: граница вертикали.

Value objects проверяют себя в конструкторе. Деньги хранятся в копейках: в SQLite нет точного DECIMAL. Порог «без звонка» — доменная политика, а не if в контроллере.

Один сценарий — одна команда и один обработчик. Транзакция, права, загрузка, вызов агрегата, сохранение, публикация событий. Никакой логики статусов здесь нет, она в домене.

Порты на языке домена: свои Page и Slice, никаких типов Spring Data. Запись идёт через агрегат, чтение для доски и списков через плоские проекции (CQRS-lite), без загрузки всего агрегата.

Доменные события идут через Spring. Слушатели срабатывают после коммита: если транзакция откатилась, доска не покажет несуществующий статус. Вместо каскадов оркестратора остаётся одно правило в агрегате.

Адаптер порта. Сущность наружу не выходит: маппинг через snapshot агрегата. Версию сверяем явно: при копировании полей в загруженную сущность Hibernate иначе молча перезапишет чужие изменения.

UUID как текст, деньги в копейках, статус строкой, @Version для оптимистичной блокировки. Позже, при переходе на PostgreSQL, сущность почти не меняется.

Миграции пишем руками, ddl-auto: validate. Таблицы STRICT, чтобы SQLite не принимал текст в числовую колонку.

Одна база в папке данных пользователя. WAL позволяет читать, пока идёт запись. Бэкап — VACUUM INTO без остановки приложения: при старте, раз в день и при закрытии, хранится 14 копий.

Недостающая часть стартера. Spring поднимается в init() (поток лаунчера, не FX), окно отдаётся приложению событием. Класс с main не должен наследовать Application, иначе jar с classpath падает с «JavaFX runtime components are missing».

Замена @FXController + ScreenManager. Контроллеры prototype, FXML-загрузчик получает фабрику контроллеров из контекста: работают fx:controller и вложенные fx:include. В кэше лежит пара «узел + контроллер», а не только узел.

Правило: FX-поток не ждёт базу. Работа идёт в виртуальном потоке, результат и ошибка возвращаются в FX-поток. Одно место вместо разбросанных Platform.runLater.

Автоконфигурация объявляет бины явно, без @ComponentScan. Всё, что приложение может подменить, под @ConditionalOnMissingBean. Файл imports закрывает #8.

FXML только раскладка и ключи i18n. Стиль из CSS-токенов дизайна v1, логики нет.

Контроллер тонкий: связывает узлы со свойствами view model. Его можно не тестировать отдельно.

Состояние экрана и вызовы use cases. Тестируется обычным JUnit без запуска окна: свойства JavaFX работают и без FX-потока.

Справочники — одна заготовка экрана-таблицы (Template Method). Колонки описаны кодом на строке UI, а не аннотациями @UIColumn на доменных классах, как в legacy.

Роли фиксированные, права — перечисление. Проверка в use case, а не только скрытая кнопка: когда появится планшет, правила уже на месте.

Сессия десктопа — реализация порта CurrentActor. На LAN-сервере будет вторая реализация (токен устройства → пользователь), а use cases не изменятся.

PIN хранится хэшем BCrypt из spring-security-crypto, без остального Spring Security (Argon2 там требует BouncyCastle). Неудачная попытка должна сохраниться, поэтому исключение не откатывает транзакцию.

Только пять модулей. Плагины и веб исключены до своих фаз, папки остаются. Общие настройки в convention-плагине, а не копией в каждом модуле.

Toolchain, Spotless, Jacoco и тесты в одном месте. Позже сюда же ляжет проверка на кириллицу.

runtimeOnly на хранилище — главная строка файла. Упаковка в установщик Windows тоже здесь.

Домен тестируется без Spring и без базы. Тест читается как правило мастерской.

Сценарий целиком на фейках портов в памяти. Это критерий готовности #10.

Адаптер проверяется на настоящем SQLite-файле во временной папке с теми же миграциями, что в проде. Контейнер не нужен.

Границы внутри модулей. Первые два правила — те, без которых через полгода получится каша.

Один-два smoke-теста на ключевые экраны через TestFX. TestFX не обновлялся с февраля 2024 года, поэтому основная проверка UI — тесты view model, а для CI позже — встроенная headless-платформа JavaFX 26+.

Сквозной сценарий: «согласовать смету» проходит все слои за 11 шагов

Приёмщик позвонил клиенту, выбрал «Телефон», вписал имя и нажал «Согласовать». Каждый шаг помечен слоем, в котором он выполняется.

  1. FX-потокEstimateView.onApprove() передаёт нажатие в view model. Кнопка уже была активна только при выполненных условиях: canApprove().
  2. FX-потокEstimateViewModel.approve() ставит busy, собирает команду ApproveEstimate и отдаёт её в FxTasks.
  3. Виртуальный потокВызов ApproveEstimateHandler.handle(). Прокси Spring открывает транзакцию (@UseCase).
  4. Use caseAccessPolicy.require(ORDER_APPROVE_ESTIMATE): текущий пользователь из DesktopSession.
  5. ХранилищеJpaOrderRepository.get(): сущность → snapshot → RepairOrder.restore().
  6. Доменorder.approveEstimate(): смета фиксирует способ, кто и сумму, затем fire(APPROVE_ESTIMATE).
  7. ДоменStateMachine.fire() проверяет guard hasApproval, возвращает IN_PROGRESS. Агрегат пишет историю и копит OrderStatusChanged.
  8. Хранилищеsave() сверяет версию, обновляет сущность. Hibernate пишет UPDATE … WHERE version = ?.
  9. Use caseevents.publish(order.pullEvents()), коммит. Только после коммита срабатывают @TransactionalEventListener(AFTER_COMMIT).
  10. FX-потокBoardRefresh через Platform.runLater перерисовывает карточку на доске. В фазе 2 тот же слушатель отправит событие на планшеты по WebSocket.
  11. FX-потокКолбэк FxTasks снимает busy и показывает «Смета согласована, заказ 2026-0142». Ошибка guard-а или StaleDataException приходит сюда же и показывается понятным текстом по ключу i18n.

Пользователи: в MVP три роли и PIN на общем ПК, токены устройств в фазе 2

Сейчас в коде User с логином, паролем и ролями ADMIN, WORKER, ACCOUNTANT, а проверок прав нет. Для мастерской на одном ПК логин с паролем слишком медленный: люди меняются у стойки по десять раз в день. Предлагаю выбор пользователя плиткой и PIN, автоблокировку при простое и проверку прав в use cases.

Текущие роли: ADMIN → владелец, WORKER → механик, ACCOUNTANT убираем, его права у владельца. Приёмка — новая роль.

MVP, в текущий скоуп

  • Мастер первого запуска: владелец, его пароль и код восстановления на печать
  • Экран выбора пользователя, PIN из 4–6 цифр, хэш BCrypt
  • Блокировка после 5 ошибок на минуту, автоблокировка при простое (по умолчанию 10 минут)
  • «Сменить пользователя» в один клик, не закрывая окна
  • Три фиксированные роли, права проверяются в use case, кнопки скрываются по тем же правам
  • Кто сделал: created_by, история статусов, оплаты, движения склада
  • Владелец сбрасывает PIN и деактивирует пользователя (без удаления, история остаётся)
  • Мастер пункта работ — пользователь с ролью «механик»

Фаза 2: планшеты и LAN

  • Сопряжение устройства по QR, токен устройства, отзыв из настроек
  • Вход механика на планшете своим PIN, «мои работы»
  • Spring Security на REST и WebSocket: токен → Actor, вторая реализация CurrentActor
  • Права в push-событиях: планшет получает только свои данные
  • Журнал входов по устройствам

Фазы 3–5

  • Лимит скидки по роли, возврат только с подтверждением владельца
  • Кассовая смена на пользователя (вместе с фискальной кассой)
  • Сдельная оплата механика по закрытым работам
  • Редактор ролей и прав (фаза 5)
  • Несколько мастерских, облачные аккаунты (фаза 5)
Почему не Spring Security в десктопе. Его контекст привязан к потоку, а у нас FX-поток и виртуальные потоки. Пришлось бы включать глобальный режим, который сломается, как только в том же процессе появится LAN-сервер с чужими запросами. Свой порт CurrentActor на 20 строк решает задачу сейчас. В фазе 2 Spring Security встанет только на HTTP-сторону и будет класть Actor в тот же порт. Из Spring Security в MVP берём только spring-security-crypto для хэшей.
